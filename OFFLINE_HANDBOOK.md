# 02. ПРОДУКТ, MVP И ГРАНИЦЫ

## Product vision

Инструмент, который получает структурированные данные электронного счёта, создаёт XRechnung, проверяет его официальными правилами и понятным образом сообщает пользователю результат. В дальнейшем — принимает, показывает и сохраняет счета малого бизнеса.

## Персона и сценарий первого этапа

Разработчик/оператор локально работает с тестовым внутренним немецким B2B (Business-to-Business — между предприятиями) счётом на EUR. Вход: JSON. Результат: файл XML на диске и отчёт проверки. Ориентир на простой стандартный случай обычного НДС, но **не объявляем поддержку всех налоговых ситуаций**.

## Граница первого MVP

**Включено:**

- Структурированный ввод из JSON-файла (позднее возможно API).
- Проверка базовых полей и типов; безопасные ошибки без повреждения файлов.
- Модели данных продавца/покупателя, позиции, денежные суммы (Decimal).
- Вычисление денежных значений с тестами и документированной политикой округления, совместимой с эталонными примерами.
- Генерация XRechnung в XML UBL 2.1 для **одного подтверждённого сценария**.
- Вызов установленного KoSIT Validator, разбор результата и явный статус `passed/failed/error`.
- Регрессионные тесты на эталонных и негативных данных.

**Не включено:**

- БД, многопользовательский доступ, авторизация, SaaS и продакшен-хостинг.
- Полный список ставок/освобождений НДС, скидок, кредит-нот, трансграничных операций.
- B2G (Business-to-Government — государственные заказчики), Leitweg-ID, обмен через OZG-RE или Peppol.
- ZUGFeRD/PDF-A, CII (Cross Industry Invoice) и визуализация.
- Правовой аудит, гарантия соответствия налоговым требованиям, реальная отправка клиентам.

## Functional requirements

| ID | Требование | Готовность проверяется |
|---|---|---|
| FR-01 | Принять локальный JSON | Строго определённый путь, корректные ошибки |
| FR-02 | Проверить данные | Неверные значения отвергаются до генерации |
| FR-03 | Посчитать строки/итоги | Тесты на Decimal и округление |
| FR-04 | Собрать UBL Invoice XML | Файл формируется, namespace и поля на своих местах |
| FR-05 | Проверить KoSIT | Получен машинный и человекочитаемый отчёт |
| FR-06 | Не выдавать ложный «успех» | Отдельные ошибки чтения, XML, бизнес-правил, запуска валидатора |

## Non-functional requirements

- **NFR-01 Offline:** функции первого MVP работают без сети после одноразовой подготовки окружения.
- **NFR-02 Reproducibility:** фиксировать версии Python, зависимостей, KoSIT и правил.
- **NFR-03 Security:** не выполнять код из входного JSON/XML; защищать обработку недоверенного XML.
- **NFR-04 Auditability:** сохраняя отчёты, связывать проверку с конкретным файлом (например, SHA-256).
- **NFR-05 Learning:** дробить задачи так, чтобы было понятно зачем применяется каждый механизм Python.

## Что значит «валиден»

1. **Данные Python:** корректные типы/обязательные поля.
2. **XML:** документ синтаксически корректен (well-formed), далее XSD/схемы.
3. **XRechnung/EN 16931:** правила профиля и бизнес-проверки пройдены в KoSIT.
4. **Юридическая пригодность для конкретной операции:** отдельная оценка; успешная техническая проверка НЕ подтверждает все налоговые/договорные обстоятельства.

## MVP Done

Демонстрационный JSON превращается в XML, контрольный KoSIT с фиксированными версиями сообщает приемлемый результат для заявленного сценария, есть подтверждающие тесты, негативные кейсы и инструкция запуска из чистого окружения. До этого проект — разработка, не продукт для выставления реальных счетов.

## Архитектура первого MVP

```text
sample-data/invoice_demo.json
```

## Модель предметной области — план, а не готовая схема EN 16931

- `InvoiceDraft`: номер, дата, валюта, продавец, покупатель, позиции, назначение/ссылка покупателя.
- `Party`: идентификация и контактная информация стороны.
- `InvoiceLine`: описание, количество, код единицы, цена без налога, категория/ставка НДС.
- `CalculatedInvoice`: вычисленные итоги (не смешивать с входными значениями без проверки).
- `ValidationResult`: status, доступность валидатора, ошибки/предупреждения и пути отчётов.

**Важное:** JSON-образец в `sample-data/` — учебный контракт входа, **не полный каталог обязательных BT** (Business Term — бизнес-элемент стандарта). Нужные BT для конкретного сценария выбираются с официальной тестовой suite и подтверждаются KoSIT.

## Минимальный JSON: почему цены — строки

```json
{"quantity":"2", "net_unit_price":"50.00", "vat_percent":"19"}
```

`float` хранит двоичные приближения, что нежелательно для денег. В Python применять `Decimal("50.00")`, причём из строк, не `Decimal(0.1)`. Политику округления не придумывать «по ощущениям»: выбрать на основе EN 16931, примеров и тестов. Суммы разных ставок группировать отдельно.

## Данные на диске

`sample-data/` — фиктивные, отслеживаемые Git-данные. `runtime/incoming/`, `runtime/outgoing/`, `runtime/reports/` — содержимое создаётся локально и игнорируется Git. В дальнейшем путь сделаем конфигурируемым; сейчас это только каталог по умолчанию для CLI.

## Основные принципы

- Функции в `domain/` должны быть чистыми: не читать диск, не печатать, не знать XML.
- Ввод и преобразования отдельны от бизнес-логики.
- KoSIT — внешний процесс, результат зависит от версии установленных правил; ошибки запуска не маскировать под «счёт невалиден».
- Сгенерированный XML не считать окончательно пригодным до проверки валидатором.
- Тестировать поведение на маленьких данных и фиксировать изменения.

## Будущая БД (НЕ В MVP)

В старом C# варианте обсуждалось разделение доменных записей о счетах и физических файлов, история состояний, контрагенты и результаты проверок. При переходе к хранению вернёмся к этим идеям. Выбор PostgreSQL/SQLite сделаем на основании реального режима эксплуатации, а не потому что он был в прежнем стеке.

**Зачем:** не передавать в генератор пустой номер, обнаруживать пользовательскую ошибку как можно раньше.

### US-02: дата счёта и валюта (после проверки US-01)

# 06. ОФЛАЙН-МИНИ-КУРС ПОД РЕАЛЬНЫЕ USER STORIES

Это не справочник всех возможностей Python. Это базовые знания в порядке, в котором они понадобятся в e-rechnung. Примеры ниже **учебные и небольшие**, а не готовые решения задач.

## Урок 1. Пакет и импорт (Sprint 0, 20 минут)

- **Package (пакет):** каталог с `__init__.py`; импортируется по имени `e_rechnung`, хотя дистрибутив в `pyproject.toml` назван `e-rechnung-learning`.

Проверка: `uv run --offline python -c "import e_rechnung; print(e_rechnung.__file__)"`. Путь должен вести в твой проект `src/e_rechnung` (при editable-установке).

## Урок 2. Функции и контракты (US-01, 30 минут)

```python
def normalize_label(value: str) -> str:
    return value.strip()
```

- `def` задаёт функцию.
- `value: str` — *type hint* (аннотация типа), не автоматическая проверка при запуске.
- `-> str` — тип ожидаемого возврата.
- `.strip()` возвращает новую строку без краевых пробелов.
- `return` возвращает значение, `print` только пишет в терминал.

Попробуй вызвать с `"  A "` и с числом `5`; подумай, какая ошибка произойдёт и почему.

## Урок 3. Исключения (US-01, 25 минут)

```python
def percent_to_int(text: str) -> int:
    if not isinstance(text, str):
        raise TypeError("text must be a string")
    if not text.isdecimal():
        raise ValueError("text must contain digits")
    return int(text)
```

- `TypeError` — неподходящий **тип**.
- `ValueError` — допустимый тип, но **недопустимое значение**.
- Ввод JSON/файла может вызвать другие ошибки (`FileNotFoundError`, `JSONDecodeError`): их не прятать под универсальным `except Exception: pass`.
- `try/except` ловит исключение; применять в **границе ввода или CLI**, а не для сокрытия ошибки в доменных правилах.

## Урок 4. `pytest` и параметризация (US-01, 30 минут)

```python
import pytest

@pytest.mark.parametrize("text, expected", [("  hi ", "hi"), ("bye", "bye")])
def test_strip(text: str, expected: str) -> None:
    assert text.strip() == expected
```

- `assert` формулирует ожидаемое поведение.
- `@pytest.mark.parametrize` прогоняет функцию с разными наборами.
- Негативные примеры проверяют `with pytest.raises(ValueError): ...`.
- Имена тестов должны объяснять условие, а не быть `test1`/`test2`.

Мини-упражнение: добавь пустую строку как отдельный случай.

## Урок 5. `pathlib` и файловые пути (US-06, 30 минут)

```python
from pathlib import Path

p = Path("runtime/incoming/example.json")
print(p.exists())
```

- `Path` управляет путями на Windows/Linux.
- Здесь `runtime/...` — относительный путь от **текущего рабочего каталога процесса**. На первом этапе CLI запускать из **корня проекта**, потом можно перейти к явно заданному пути `--input`.
- `Path(__file__).resolve()` задаёт путь относительно файла, а не CWD (Current Working Directory — рабочего каталога).
- В тестах `tmp_path` даёт временный каталог без загрязнения рабочего дерева.
- `read_text(encoding="utf-8")`, `write_text(encoding="utf-8")` — явная кодировка.

## Урок 6. JSON и объекты (US-06/07, 30 минут)

```python
import json

sample = '{"number":"DEMO-1","quantity":"2"}'
record = json.loads(sample)
assert record["number"] == "DEMO-1"
```

- JSON — текст; после `loads` получаем словари/списки/строки/числа/`None`.
- На входе нельзя предполагать, что поле присутствует; реши, когда `.get()` уместен, а когда должен возникнуть понятный сбой.
- `json.load(file)` читает объект из открытого файла, `json.loads(text)` — из строки.
- В тестовом контракте денежные поля намеренно представлены **строками**.

## Урок 7. Decimal вместо float (US-04/05, 40 минут)

```python
from decimal import Decimal

price = Decimal("12.50")
quantity = Decimal("2")
net = price * quantity
assert net == Decimal("25.00")
```

- В большинстве денежных операций избегать `float`, особенно входа `Decimal(0.1)`.
- `Decimal` хранит десятичное представление.
- `quantize(Decimal("0.01"), rounding=...)` — явное округление, **но** режим/точки округления в реальном XRechnung нужно сверять с EN 16931 и эталонными случаями, а не назначать вслепую.
- Определить поведение при нуле, минусе, избыточной точности и нескольких ставках.

Мини-упражнение: вывести произведение `Decimal("1.25") * Decimal("3")` и объяснить разницу с `float`.

## Урок 8. `dataclass` и разделение ответственности (US-07, 30 минут)

```python
from dataclasses import dataclass
from decimal import Decimal

@dataclass(frozen=True)
class ExampleItem:
    title: str
    net_price: Decimal
```

- Dataclass уменьшает шаблонный код моделей.
- `frozen=True` запрещает обычное присваивание полей после создания; это не заменяет валидацию правильности значений.
- На одном уровне отделять **исходные данные** от **вычисленного результата**.

## Урок 9. XML и namespace (US-08/09, 40 минут)

```python
from xml.etree import ElementTree as ET

root = ET.Element("example")
ET.SubElement(root, "note").text = "test"
print(ET.tostring(root, encoding="unicode"))
```

- XML — дерево элементов и атрибутов.
- У XRechnung UBL имеются **пространства имён** (XML namespaces) и **строгие правила** содержания.
- Пример выше не является UBL/XRechnung. Не подменять официальный mapping «на глаз».
- Не собирать XML строковой конкатенацией пользовательских значений.
- Для недоверенного входящего XML рассмотреть защищённый парсер, лимиты размера/ресурсов; обычный `ElementTree` не считается автоматически безопасным (см. официальные предупреждения Python).

## Урок 10. `subprocess` и коды выхода (US-11, 35 минут)

```python
import subprocess

completed = subprocess.run(
    ["python", "--version"],
    capture_output=True,
    text=True,
    timeout=15,
    check=False,
)
print(completed.returncode, completed.stdout, completed.stderr)
```

- CLI (Command-Line Interface) получает аргументы **списком**, а не собранной строкой с `shell=True`.
- `returncode` — код выхода процесса; нельзя автоматически считать любой ненулевой код «несоответствием счёта»: отдельно обрабатывать сбой инфраструктуры.
- `timeout` ограничивает зависший процесс.
- В будущем вместо Python будет Java `-jar` KoSIT.

# 07. OFFLINE SETUP: не зависеть от интернета на вахте

## Выбранный основной путь: `uv`

Разработчик уже работал с Python 3.13, `uv`, `pytest` на Windows. Здесь используем `uv` для локальной установки `src`-пакета и фиксации разрешённых зависимостей. `pyproject.toml` описывает проект, `uv.lock` фиксирует конкретные версии, `.venv` хранит установленные пакеты на **текущей машине**. Не коммитим `.venv`.

### A. Когда сеть есть (в корне проекта)

```powershell
python --version
uv --version
uv sync
uv run pytest -q
uv run ruff check .
uv run python -m e_rechnung --help
```

`uv sync` создаст или обновит `uv.lock`, построит/установит локальный пакет и установит dev-инструменты. Сохрани lock в Git.

### B. Перед отключением интернета (в том же каталоге)

```powershell
uv sync --locked --offline
uv run --offline pytest -q
uv run --offline python -m e_rechnung --version
```

**Если команды не выполнились — среда ещё не готова к офлайну.** Проверка обязательна. `--offline` запрещает сетевые запросы. При отсутствии нужных пакетов/колёс требуется ещё один онлайн-сеанс.

### C. Во время работы без сети

```powershell
uv run --offline pytest -q
uv run --offline ruff check .
uv run --offline python -m e_rechnung --help
```

Не делать `uv sync` без `--offline` при слабом интернете. Не обновлять зависимость без причины посреди спринта. После изменения `pyproject.toml` может потребоваться доступ к кэшу/сети и обновление lock-файла.

## На другой/чистой машине

Одного `uv.lock` недостаточно: требуются сам Python, `uv`, **физические пакеты** (wheel и backend сборки) или предварительно перенесённый кэш совместимой платформы. Также могут понадобиться Java и KoSIT-файлы. Вариант без кэша: заранее загрузить на онлайн-машине нужные wheel для **той же ОС, архитектуры и Python**, затем проверить установку строго офлайн.

Загрузка для pip в отдельную папку при наличии сети (пример, **не заменяет проверку совместимости**):

```powershell
python -m pip download --dest .offline-wheels pytest ruff setuptools wheel
```

При отсутствии `pip`/его кэша/совместимых wheel нельзя обещать автономную установку на произвольном компьютере. `.offline-wheels` не включается в этот комплект.

## Альтернатива без `uv`: стандартные `venv` и `pip`

На Windows в PowerShell (из корня проекта):

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -e . pytest ruff
.\.venv\Scripts\python.exe -m pytest -q
```

Первые установки **могут требовать сеть**. Для офлайна готовить wheel заранее и использовать `pip --no-index --find-links <каталог-с-wheel>`; настройка сборочного backend (`setuptools`, `wheel`) также должна быть доступна. Не использовать этот вариант одновременно с `uv sync` в том же окружении без понимания последствий.

# 08. НЕМЕЦКОЕ E-RECHNUNG: ЧТО ПРОВЕРЕНО НА 08.10.2026

## 1. Правовой статус (Германия, B2B)

Источник: Федеральное министерство финансов Германии (**BMF, Bundesministerium der Finanzen**), официальные FAQ, редакция **23.03.2026**:  
https://www.bundesfinanzministerium.de/Content/DE/FAQ/e-rechnung.html

- С 01.01.2025 электронный счёт в рассматриваемом правовом смысле — **структурированный** формат, пригодный для электронной обработки. Обычный PDF без структурированных данных — *sonstige Rechnung*, а не E-Rechnung.
- Для немецких внутренних B2B-операций введены переходные периоды для **выставления**: до 31.12.2026 разрешены другие формы; для эмитентов с оборотом предыдущего года **не более 800 000 EUR** соответствующая отсрочка — до 31.12.2027; также действует отдельное переходное правило для некоторых EDI-операций. Детали/исключения — в FAQ, вопрос 11.
- Для **получения** E-Rechnung способность принимать её требуется с 01.01.2025, в том числе для Kleinunternehmer; технически в FAQ достаточно почтового ящика, вопрос 12.
- Форматы **XRechnung** и **ZUGFeRD** (с применимыми профилями) названы как типичные соответствующие варианты; обычный PDF таким не является, вопрос 7.
- По §14b UStG исходящие/входящие счета хранятся **8 лет**; структурированная оригинальная часть должна сохраняться в неизменной первоначальной форме, вопрос 13. Для реального архива потребуются дополнительные организационные меры.
- BMF прямо разграничивает налоговую позицию и техническую реализацию: FAQ министерства не является техническим руководством программиста.

**Не распространяй эти правила без проверки на трансграничные сделки, потребителей, особые налоги и счета госорганам.**

## 2. XRechnung и UBL

- **EN 16931:** европейская серия стандартов по семантической модели электронного счёта.
- **XRechnung:** немецкая CIUS (Core Invoice Usage Specification — национальная спецификация применения ядра) EN 16931.
- **UBL (Universal Business Language) 2.1:** поддерживаемый XML-синтаксис, выбранный для первого проекта. Второй распространённый синтаксис — CII (Cross Industry Invoice), его откладываем.
- **KoSIT (Koordinierungsstelle für IT-Standards):** национальная координация спецификаций, правил валидации и тестов.

## Где хранить (Windows)

```text
<корень проекта>/tools/kosit/
    validator-1.6.3-standalone.jar
    configuration/                 <- сюда распаковать config ZIP
        scenarios.xml              <- найти фактический путь после распаковки
    reference/
        01.01a-INVOICE_ubl.xml
```

### Порядок действий

1. Проверить `java -version`: установлен Java 11+ (и если возможно, локально сохранён установщик).
2. Скачать JAR и configuration ZIP по указанным официальным страницам.
3. Распаковать config ZIP в `tools/kosit/configuration`. **Проверить**, где реально оказался `scenarios.xml` (архив может иметь собственную внутреннюю директорию).
4. Положить эталонный XML в `tools/kosit/reference`.
5. В PowerShell перейти в директорию, где лежит **`scenarios.xml`**. Пусть это текущий каталог `$PWD`.
6. Запустить валидатор — в команде ниже **заменить** пути `C:\...` фактическими абсолютными путями:

```powershell
$rulesDirectory = (Get-Location).Path
java -jar "C:\...\tools\kosit\validator-1.6.3-standalone.jar" `
  -s scenarios.xml `
  -r $rulesDirectory `
  -h "C:\...\tools\kosit\reference\01.01a-INVOICE_ubl.xml"
```

В официальном примере результат записывается в `...-report.xml` и `...-report.html`. Смотри **фактические** файлы/сообщения для установленной версии и сценария. Для будущего Python-adapter явно выбирай директорию работы и назначения отчётов, **не полагайся на случайный CWD**.

- [ ] Java установлена и версия проверена.
- [ ] Известны точные версии JAR и конфигурации.

Использовать `subprocess.run(["java", "-jar", jar, "-s", scenarios, "-r", root, "-h", xml], capture_output=True, text=True, timeout=..., check=False)`; **не использовать `shell=True`** для пользовательских путей. # 10. ADR (Architecture Decision Record — журнал архитектурных решений) И РИСКИ

## ADR-001. Python вместо C# (принято 08.10.2026)

**Контекст:** ранее проект проектировался на ASP.NET Core. Сейчас основная цель — изучать Python через реальную задачу.
**Решение:** новое ядро писать на Python, прежние C# решения не переносить автоматически.
**Последствия:** полезные предметные требования сохраняются, а технологические модули перепроектируются.

## ADR-002. Один узкий MVP (принято для старта)

**Решение:** JSON → UBL 2.1 XRechnung → KoSIT, без БД, хостинга и графического UI на первом этапе.
**Причина:** закончить сквозной функционал, прежде чем расширять систему.
**Проверка:** есть один реальный вертикальный срез с официальным отчётом, а не только заготовки пакетов.

## ADR-003. CLI перед web (рабочее предположение)

**Решение:** сначала локальная CLI-оболочка, потом при необходимости API/UI.
**Причина:** легко запускать/дебажить офлайн.
**Пересмотреть:** когда появится подтверждённый сценарий пользователя веб-интерфейса.

## ADR-004. `src` layout + `uv` + `pytest` (принято в стартере)

**Решение:** правильный пакет через pyproject + тесты, без ручного `PYTHONPATH`.
**Причина:** понятная структура, навыки промышленной упаковки, привычный workflow.
**Последствия:** нужно заранее закэшировать зависимости; в отключённой сети новый lock невозможно достоверно разрешить без нужных пакетов.

## ADR-005. KoSIT как эталонная проверка (принято)

**Решение:** валидность XRechnung подтверждать отдельным валидатором и версионированными правилами KoSIT.
**Причина:** XML-парсер и собственные проверки не реализуют весь набор норм.
**Последствия:** Java + файлы правил нужно загрузить заранее, версия влияет на воспроизводимость.

# 13. WORK LOG — журнал учебного процесса и прогресса

В конце каждого учебного блока заполнять **3–5 строк**, не превращать в отчёт на страницу.

## Шаблон записи

```text
Дата: ГГГГ-ММ-ДД
Sprint / User Story: US-..
Сделано (факт): ...
Команда и итог тестов: ...
Что сам понял / где ошибся: ...
Следующий один шаг: ...
```

## Первая запись — после распаковки

```text
Дата: ...
Sprint / User Story: Sprint 0 / US-00
Сделано (факт): ...
Команда и итог тестов: ...
Что сам понял: ...
Следующий один шаг: US-01 — проверить номер счёта
```

## Sprint Review и Retrospective

**Review (обзор результата):** покажи один работающий пример вход → выход и результат тестов.  
**Retrospective (ретроспектива):** ответь кратко: что помогло понять Python; где возникло затруднение; какую одну практику изменить в следующем спринте.

### Признаки, что задача слишком крупная

- Более одной новой для тебя подсистемы одновременно (например XML, KoSIT, FastAPI и БД).
- Нельзя объяснить тесты и критерии завершения.
- Не ясно, какой файл создать и что он принимает/возвращает.

В таком случае разбить задачу, а не загружать одновременно всё из бэклога.

# 14. ПРАВИЛА ПРОВЕРКИ И ГОТОВНОСТИ

## Checkpoint разработки

Перед завершением User Story:

- [ ] Я могу объяснить **что принимает**, **что возвращает** и **почему** моя функция устроена так.
- [ ] У неё есть позитивный и негативный тест.
- [ ] Ошибки определены: неправильный тип, значение, путь, внешний инструмент.
- [ ] `uv run --offline pytest -q` проходит на моём рабочем окружении.
- [ ] `uv run --offline ruff check .` без замечаний.
- [ ] Я не использовал `PYTHONPATH` вручную, неожиданные абсолютные `C:\...` в исходниках, `except: pass`.
- [ ] Секретов и реальных счетов в Git нет.
- [ ] Сделан небольшой коммит, документация/backlog обновлены.

## Что не является доказательством готового счёта

- «XML файл создан».
- «Браузер показал XML».
- «`ElementTree.parse` не упал».
- «Мой Python-код проверил несколько обязательных полей».
- «Он похож на образец».

Для поддерживаемого документного сценария нужен **реальный отчёт KoSIT по правильной версии правил**. Для коммерческого применения нужна дополнительная проверка законности, условий обмена, хранения и налоговой ситуации.

## Контроль качества дорожной карты

Перед началом каждого Epic спросить: чем следующий шаг проверяется? где точно создавать файлы? что скачать заранее? какие исходные знания нужны? как ограничена область? Если ответов нет, уточнить карточку **до начала кода**.
